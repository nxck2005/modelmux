## Milestone 1A: validated configuration

### Scope

Implement the validated TOML configuration and allowed model catalog required
by the routing core. Policy evaluation, judge calls, and routing decisions are
not implemented.

### Created

- `src/modelmux/config.py`: frozen Pydantic configuration models, the
  `load_config` TOML loader, and `ConfigError` with sanitized messages.
- `examples/router.toml`: commented example with clearly fictional provider
  and model identifiers.
- `tests/test_config.py`: 27 focused loading and validation tests.
- A `Run tests` (`uv run pytest`) step in `.github/workflows/ci.yml`; the job
  structure is unchanged.
- A configuration section in `README.md` and a refreshed `tests/README.md`.

### Configuration decisions

- TOML keys: `version = 1`, `[router]`, `[judge]` with `[judge.static.scores]`
  and `[judge.jev]`, `[profiles.<id>]` with optional `[profiles.<id>.output]`,
  and ordered `[[policy.rules]]`.
- `[router]` requires all four profile references (`default`,
  `judgment_fallback`, `compatibility_fallback`, `economy`), and each must name
  a configured profile. Requiring them explicitly keeps the router from
  inferring a profile; when each reference is used arrives with the router.
- Policy conditions use only the four semantic fields and `gt`/`gte`/`lt`/
  `lte`; values are finite and in [0, 1]. Rule IDs are unique and conditions
  are nonempty. First-match evaluation is not implemented yet.
- `judge.selection` accepts `static`, `rules`, or `jev`; `deadline_ms`
  defaults to 1500. Selecting `static` or `jev` requires the matching section.
- `judge.jev.api_key_env` is an environment variable name constrained to
  `[A-Za-z_][A-Za-z0-9_]*`. Loading never reads the environment; the Jev judge
  resolves the credential when instantiated.
- Provider/model IDs, reasoning effort (opaque provider value), capabilities,
  rank, output default/max, and context limit are user configuration. There is
  no built-in model catalog. Any configured `output.default` must not exceed
  `output.max`.
- `ConfigError` carries field-path messages derived from Pydantic error
  locations and static messages. The underlying parser/validation exception is
  suppressed (`from None`) so credential values and raw configuration
  fragments cannot leak through tracebacks.
- Validation is syntactic and internal only. It cannot verify provider account
  access to a model, real context windows, or support for a reasoning setting.

## Milestone 1B: task-state extraction and offline judges

### Scope

A caller can supply harness-neutral task content, obtain a bounded TaskState,
and evaluate it with a static or rule-based judge. Policy evaluation, routing,
Jev, the service, CLI, and harness integration remain unimplemented.

### Created

- `src/modelmux/types.py`: shared `Identifier`/`Score`/`NonNegativeInt`
  aliases plus `TaskProfile`, `BoundedText`, `TaskState`, `ObservationKind`,
  `JudgeResult`, and the `task-profile-v1` question version.
- `src/modelmux/state.py`: `MessageRecord`, `ToolRecord`, and the
  deterministic `extract_task_state` function.
- `src/modelmux/judges/base.py`: the `TaskJudge` Protocol.
- `src/modelmux/judges/static.py` and `judges/rules.py`: offline judges.
- `tests/test_types.py`, `tests/test_state.py`, `tests/test_judges.py`.
- README section and refreshed `tests/README.md`.
- `config.py` now imports the shared `Identifier`, `Score`, and
  `NonNegativeInt` aliases from `types.py` instead of defining them locally.

### Decisions

- Extraction caps: latest user 6,000 characters; instructions 2,000; recent
  history 3,000; tool excerpts 1,000 (12,000 total). A block longer than the
  remaining budget keeps head and tail around a fixed truncation marker that
  is counted inside the cap. History is selected newest-first and restored to
  chronological order.
- `BoundedText.omitted_chars` counts original characters not retained; the
  marker occupies part of the cap, so it is not simply
  `len(original) - len(retained)`.
- `TaskState` records the exact supplied message count and UTF-8 text bytes,
  exact tool count and names, and explicit omission counts. These describe the
  supplied window only, not the session or the provider request. No tokenizer
  or generated summaries are used.
- Score validation now rejects booleans and non-numeric values as well as NaN,
  infinities, and values outside [0, 1]. This also strengthens configured
  static-judge scores from 1A.
- `StaticTaskJudge` returns configured scores with
  `observation_kind=heuristic`; `RuleBasedTaskJudge` uses one small cue table,
  defaults to normal-compatible scores, and treats explicitly mechanical work
  as routine only when no reasoning or high-consequence cue is present.
- Judges return `judge_id` and the question version, leave `model_id` None, and
  never see the model catalog. `JudgeResult` usage/cost reporting is deferred
  until a judge can observe it.

## Milestone 1C: routing core using the offline judges

### Scope

A caller can supply task state, a current effective configuration, and
available capabilities, then receive a structured routing decision. Jev,
generation, HTTP service, CLI, and harness integration remain unimplemented.

### Created

- `src/modelmux/policy.py`: pure first-match evaluation over configured rules
  and comparison operators.
- `src/modelmux/router.py`: `EventKind`, `RouteAction`, `ReasonCode`,
  `EffectiveConfiguration`, `ProfileAvailability`, `RoutingRequest`,
  `RouteDecision`, and `Router`.
- `src/modelmux/judges/base.py`: `JudgeError` for expected judge failures.
- `src/modelmux/judges/__init__.py`: `build_judge` for the configured
  static/rules judge; Jev raises as unimplemented.
- `tests/test_policy.py` and `tests/test_router.py`, including one end-to-end
  offline scenario from `examples/router.toml` through the static judge.
- README routing example and this handoff.

### Decisions

- Eligibility is the intersection of configured profiles and caller-reported
  availability, and required capabilities must appear in both the report and
  the configured profile. Prompt text never authorizes a model, and judge
  output is never used as a model identifier.
- Exactly one compatibility fallback is attempted, and only when the switch is
  safe (`safe_to_apply_before_generation`) and the history is compatible.
  Otherwise the router defers with the current route or stops.
- `keep` and `defer` leave the current configuration in effect;
  `RouteDecision.continues_with_current` states that explicitly. `stop` means
  no valid configuration can execute. `switch` carries a fully resolved
  profile/provider/model/effort/output target; unresolved context fit is not
  claimed.
- Incomplete judge state (missing or truncated latest user text, or any
  omitted/truncated block) vetoes an economy-profile candidate. The veto
  redirects to the router default; if the default is also the economy profile
  the router stops with `incomplete_state`.
- Escalation requires a higher-rank candidate, an eligible profile, a safe
  boundary, and history that can move (portable, or the same provider). Equal
  or lower rank keeps the current route; there is no automatic de-escalation.
- Tool continuations never call the judge. An unavailable or unconfigured
  current route stops with `invalid_current` rather than switching mid-loop.
- Expected judge failures are `JudgeError` and the configured deadline
  (`TimeoutError`). They retain an eligible current route, otherwise use the
  configured judgment fallback. Other exceptions and caller cancellation
  propagate, and `asyncio.timeout` cancels the judge call in place.
- Application-failure events, per-session sequencing, acknowledgments, TTL
  state, config digests, notification flags, and usage/cost are deferred to
  the integration or service milestones.

## Milestone 1C review repair

### Scope

Fix five review findings in the routing core: history and safe-boundary checks
on every proposed switch, validation of the actual current configuration,
escalation-only fallback behavior, the incomplete-state economy veto on
fallbacks, and factual compatibility checks for effort support, output
ceilings, and context limits. No Jev, service, CLI, or harness work.

### Behavior changes

- Every proposed switch now passes the same safe-boundary and history checks,
  including compatibility and judgment fallbacks. When the current
  configuration is unusable and the fallback switch is unsafe or
  history-incompatible, the router stops instead of deferring with an
  unusable route.
- The current effective configuration is validated against the configured
  profile (provider, model, effort), availability, required capabilities,
  output bounds, and context facts before it can be retained. Effective output
  limits may differ from the configured default but must stay within the known
  ceiling. Invalid current routes stop tool continuations without rejudging or
  switching, and use recovery or the judgment fallback on new turns.
- A compatibility fallback may not downgrade a valid current configuration or
  cause an equal-rank switch; it only escalates relative to the current route
  when the candidate is unavailable. Recovery from an unusable current
  configuration may still use a lower-rank fallback.
- The incomplete-state economy veto applies to compatibility and judgment
  fallback proposals, not only the original candidate. A compatible
  already-applied economy route is still retained on judge failure.
- `ProfileAvailability` may carry factual `reasoning_efforts`,
  `max_output_tokens`, and `context_limit`; `RoutingRequest` may carry
  `required_output_tokens` and `current_input_tokens`. Unknown facts stay
  `None` and never cause a positive rejection, and known incompatibilities
  reject candidates, current configurations, and fallbacks alike. Required
  output raises the resolved effective limit within the known ceiling and is
  never silently shrunk. Context checks use only caller-supplied token facts,
  never the bounded judge state. Known input that exceeds a known context
  limit is rejected even when the output reservation is unknown; otherwise
  the effective output limit is added when known, or the explicit required
  output when known. Unknown output is not treated as a zero-token
  reservation and no fit is claimed for it.
